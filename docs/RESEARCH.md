# llm-wiki: Research Synthesis & Design Report

## 1. Executive summary

**What we found.** "LLM wiki" is now a named, viral pattern ([Karpathy's April 2026 gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f), 5k+ stars in days) — but the discourse defaults to *personal* knowledge bases; the codebase application is a confluence with an older auto-doc lineage (autodoc → mutable.ai → [DeepWiki](https://cognition.ai/blog/deepwiki) → [Google Code Wiki](https://developers.googleblog.com/introducing-code-wiki-accelerating-your-code-understanding/)). That lineage has converged on citations + diagrams + chat, and reliably fails in five documented ways: hallucinations behind valid-looking citations, shallow big-file-weighted pages, handwavy diagrams, opaque or destructive regeneration, and no human edit path. Memory-bank systems (Cline et al.) prove the in-repo markdown methodology but rot because they mix session state with durable knowledge and have **zero mechanical staleness detection**. Mechanical code↔doc validity checking exists only in adjacent shapes — Swimm's proprietary snippet anchors and Dosu's CI freshness scoring — no in-repo, agent-maintained, plain-markdown wiki system ties page validity to code versions. The production reference implementation (39 managed pages, git-blob-SHA `covers` freshness, coverage inversion, machine-validated Mermaid flows, dual-audience pages) already exceeds the entire shipping field on grounding and freshness; ~80% of it is repo-generic.

**What we recommend.** Ship llm-wiki as a **Claude Code plugin whose init skill vendors a per-repo layer** (wiki skeleton, schema doc, zero-dependency check scripts, default-enabled non-blocking post-commit hook, manifest for safe updates), positioned explicitly as "Karpathy's llm-wiki pattern applied to a codebase: the raw-source layer is the repo itself." Core loop: deterministic blob-SHA anchors trigger, cheap lints classify, the LLM refreshes only flagged pages with reviewable diffs. Default taxonomy: the reference repo's six categories plus `howto/` and a glossary, with Diátaxis encoded as frontmatter, not folders. Connector layer: a two-tier versioned contract — the markdown corpus itself for simple emitters, a JSON-Schema'd `wiki-index.json` for staleness-aware ones; ship the generated `index.md` first, llms.txt/Quartz/MCP second. Two deliberate fixes over the reference repo: tooling-owned status fields leave the tracked tree entirely (status is always computed, killing the dirty-tree/merge-conflict pain), and `index.md` becomes a generated artifact (killing triple bookkeeping).

## 2. The concept and where it stands

**Karpathy's lineage is precise.** March 2025: docs should be "a single your_project.md text file… intended to go into the context window of an LLM" ([tweet](https://x.com/karpathy/status/1899876370492383450)) — single-file framing. February 2026: the DeepWiki post argues derived docs beat stale human docs because "the code is the source of truth" ([tweet](https://x.com/karpathy/status/2021633574089416993)). April 2026: the [llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) (~16–17M views on the [announcing tweet](https://x.com/karpathy/status/2039805659525644595)) crystallizes the pattern: **three layers** (immutable raw sources → LLM-owned interlinked markdown wiki → a schema doc "like CLAUDE.md or AGENTS.md"), **three operations** (ingest / query / lint), two special files (`index.md` catalog, append-only `log.md`), explicit anti-RAG framing ("the wiki is a persistent, compounding artifact" — answers get filed back as pages), and distribution as an "idea file" the reader's agent instantiates. Crucially, the gist targets *personal* knowledge bases; mid-2026 tutorials and implementations overwhelmingly read it that way ([MindStudio](https://www.mindstudio.ai/blog/andrej-karpathy-llm-wiki-knowledge-base-claude-code), [danvega/karpathy-wiki](https://github.com/danvega/karpathy-wiki)). A community skill named "llm-wiki" **will be read against the gist** and must position itself in one line as the repo-flavored application: same three layers, but the immutable source layer *is* the codebase, so provenance = code citations + blob-SHA drift hashes instead of copied sources.

**Context-file norms define the slot the wiki fills.** [AGENTS.md](https://agents.md/) (Aug 2025, 60k+ repos, [Linux Foundation stewardship](https://openai.com/index/agentic-ai-foundation/) since Dec 2025) is the cross-tool "README for agents"; Claude Code still natively reads CLAUDE.md, with the [symlink/import pattern](https://claudelog.com/faqs/claude-md-agents-md-symlink/) as interop; [GitHub Copilot's repository custom instructions](https://docs.github.com/en/copilot/customizing-copilot/adding-repository-custom-instructions-for-github-copilot) (`.github/copilot-instructions.md`, plus path-scoped `*.instructions.md` files with `applyTo` globs) extend the same norm to the Copilot ecosystem. [llms.txt](https://llmstxt.org/) (Howard, Sept 2024) won docs-platform adoption via Mintlify but failed as a crawler standard — Google's Mueller [compared it to the keywords meta tag](https://www.seroundtable.com/google-does-not-endorse-llms-txt-40789.html); its surviving value is as an agent navigation manifest you point an agent at. The strongest 2025–26 norm is **progressive disclosure**: keep the always-loaded root file tiny (<60–300 lines, "prefer pointers to copies" — [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)) and push depth into an on-demand docs directory. Academic support: the [Codified Context study](https://arxiv.org/abs/2602.20478) (283 sessions, 108k LOC) validates a hot always-loaded constitution + cold on-demand knowledge base. **The wiki is the cold tier** — the scaled-up, schema-tized agent_docs/.

**Wiki vs context file, per the converged discourse:** (1) persistence + compounding — query results filed back as pages; (2) navigation by index + interlinks instead of always-loaded context or embedding search (auditable, infra-free up to ~100 pages, per the gist); (3) per-claim provenance to code, which rule files don't carry; (4) an explicit maintenance loop (lint: contradictions, stale claims, orphans) — single files rot silently; (5) schema separated from content. The root file remains the entry point and must only ever hold a pointer block.

**What the best get right.** Citations as the trust mechanism (Auto Wiki → DeepWiki → Code Wiki, independently converged); two-phase plan-then-generate init (deepwiki-open); structure-aware decomposition over embedding-RAG (CodeWiki beats DeepWiki on quality; [Driver AI](https://techcrunch.com/2024/10/08/driver-launches-an-ai-powered-platform-for-creating-technical-documentation/)'s bottom-up symbol→folder→codebase synthesis); change-scoped incremental refresh (RepoAgent, CodeWiki `--update`, [RepoDoc: 73% time / 77% token savings, 97% update recall](https://arxiv.org/html/2604.26523v1)); deterministic multi-signal anchoring with confidence-tiered response (Swimm); steering configs with page caps that force curation (DeepWiki wiki.json); wikis as agent infrastructure via MCP (DeepWiki, [OpenDeepWiki](https://github.com/AIDotNet/OpenDeepWiki)).

**Where they systematically fail.** (1) *Hallucination behind citations* — DeepWiki claimed LibreOffice uses Buck; Auto Wiki invented a CPython "tiered interpreter"; Cognition admits they ["can never exclude hallucinations entirely"](https://news.ycombinator.com/item?id=45002092). (2) *Shallow, overlapping, big-file-weighted pages* — the universal complaint ([deepwiki-open #230](https://github.com/AsyncFuncAI/deepwiki-open/issues/230), Code Wiki "oscillates between too vague and too specific"). (3) *Unvalidated diagrams* — "too handwavy", "not engineering quality". (4) *Opaque or destructive refresh* — DeepWiki lags days; Code Wiki rewrites everything per commit. (5) *No human editorial path* — the recurring "this is not a wiki" objection from 2024 through 2025, sharpened by the [passo.uno critique](https://passo.uno/ai-wikis-docs-teather-as-a-service/): auto-wikis are "documentation theater" with no accountable intent. A critical empirical caution underlies all of this: [LLMs have a systematic blind spot for "implementation drift"](https://arxiv.org/pdf/2604.03447) — when only the code changes while the documentation text remains plausible, detection drops by 7–42 percentage points; the study's conclusion is that current LLMs are better at auditing natural-language specifications than at detecting subtle code-level drift. **Deterministic anchors, not LLM judgment, must drive triggering.** Market signal: mutable.ai died, autodoc was abandoned, Swimm pivoted to COBOL, [Cody was killed](https://sourcegraph.com/blog/changes-to-cody-free-pro-and-enterprise-starter-plans) — standalone hosted doc products struggle; in-repo content riding the user's existing agent subscription has no cost structure to collapse.

**No shipping tool combines** machine-verifiable per-claim grounding + incremental change-scoped refresh + human editability + validated diagrams + in-repo plain-markdown storage. autodoc held the in-repo-markdown corner alone in 2023 and died of having none of the other four; that intersection is the product.

## 4. The reference implementation

The production repo (39 managed pages under `docs/Shopify NL Wiki/`, count verified by `pnpm wiki:check` at publish time — down from 43 at draft time after a product-removal merge; that the count drifted between draft and review is precisely the failure mode the skill's freshness machinery exists to catch) does four things the landscape does not:

1. **Machine-checkable freshness via git-blob-SHA `covers` lists.** Every page declares the files it covers with `git hash-object` SHAs; a 142-line stdlib-only Node script re-hashes and classifies pages fresh/stale/unmanaged/malformed. No surveyed *in-repo, agent-maintained, plain-markdown wiki system* ties page validity to code versions — the closest substitutes are Swimm's deterministic snippet/token anchors (proprietary SaaS, human-authored docs), Dosu's frontmatter-declared `sources:` globs scored in CI (a scoring service, not a wiki), Kiro's live file refs, Malloy's [manual LLM verify ritual](https://docs.malloydata.dev/blog/2026-01-13-context-md-convention/), and DeepWiki's blunt regeneration.
2. **Coverage inversion.** Freshness is blind to files *no* page covers (this blind spot let four whole subsystems ship pageless while checks stayed green); `check-coverage` subtracts all covers paths from config-scoped source files, flags "page-worthy" directory clusters, and a `--since` mode gives a commit-time new-feature→new-page nudge.
3. **Machine-validated flow diagrams.** Flow pages carry an invisible `flow-meta` manifest; a checker dispatches by kind to extractors that rebuild ground truth from the code (string-literal `callActivity` names, the Express mount graph, C# `[Function]` attributes) and enforce either **set-equality** or **anchor-existence** contracts — with the honesty gradient explicitly documented. This answers the "handwavy diagrams" failure class directly; nothing shipping does it.
4. **A schema doc + authoring discipline.** Citation rules ("never narrate runtime behaviour you have not read in the code"), the `TODO-VERIFY` demotion convention, the 30-second-grep distillation test, dual-audience hybrid pages (`audience: [dev, admin]` + bounded `## For operators` sections — chosen over a parallel wiki because parallel layers double maintenance and can't be freshness-tracked), and a standing REFRESH-PROMPT that diffs covered files against `generated_at_commit` and re-verifies every citation.

What the landscape has that it lacks: a steering manifest that machines actually consume (its `wiki.config.yml` is mostly decorative), MCP/site/llms.txt connectors, a three-state staleness classification (Swimm), TTLs for unanchored concept pages (Dosu), and an append-only `log.md` (Karpathy).

**Pain points to fix in the skill** (all observed in production): byte-coarse SHA freshness blind to line drift and renames; manual `git hash-object` bookkeeping (no stamping helper — the largest authoring friction and main source of checker-gate failures); tooling-owned `status:`/`last_checked:` frontmatter that dirties the tree post-commit and is a merge-conflict magnet; default-off local-only hook with zero CI presence ("status: fresh can be stale-in-reality on any clone"); triple-duplicated page summaries (frontmatter / index.md / manifest) with index.md as a single-writer bottleneck; hardcoded wiki path in every script (renaming the dir touched everything); extractor validity resting on unchecked code conventions; no deletion/archival story; bespoke workflow-runner DSL that can't ship as-is. Roughly 80% of the machinery is repo-generic; the project-specific 20% is concentrated in the three flow extractors and a handful of constants — exactly what becomes config + plugins.

## 5. Recommended defaults for the skill

### 5a. Folder taxonomy + frontmatter schema

**Taxonomy (opinionated default; init lets users trim):**

```
<wiki-root>/
  index.md            # GENERATED catalog: one-line summary per page (llms.txt-shaped)
  log.md              # append-only: "## [date] op | subject" (Karpathy)
  GLOSSARY.md         # arc42 §12; cheap for an LLM to maintain, high retrieval value
  AGENTS.md           # the schema doc: taxonomy, frontmatter, authoring/refresh rules
                      #   (init symlinks CLAUDE.md → AGENTS.md so Claude Code auto-loads it)
  wiki.config.yml     # machine-authoritative: paths, scope globs, tunables, validators, planned pages
  architecture/       # C4 L1–L2 / arc42 §3+§5: system context, containers, building blocks
  concepts/           # cross-cutting concepts no single file owns (arc42 §8)
  features/           # per-feature design + history (design-doc tradition; no classical analog)
  flows/              # runtime views; machine-validated Mermaid (arc42 §6)
  decisions/          # ADRs: immutable, statused, supersedable (MADR-lite)
  gotchas/            # hard-won knowledge that cost someone time (arc42 §11)
  howto/              # runbooks, deploy procedures, manual triggers (Diátaxis task quadrant)
  _templates/  _audit/   # tooling-skipped
```

**Justification.** Domain-shaped top level, not Diátaxis quadrants — [Diátaxis itself rejects quadrants-as-folders](https://diataxis.fr/complex-hierarchies/) for complex sets; instead encode the Diátaxis mode as a frontmatter `kind:` field and lint for mode drift, the pattern [documentation.ai operationalizes](https://documentation.ai/blog/diataxis-framework). The six reference-repo categories map almost 1:1 onto arc42 sections (use [arc42's 12 sections](https://arc42.org/overview) as the init/audit completeness checklist, never as document structure). Two additions vs the reference repo, adjudicating the doc-frameworks angle in favor: `howto/` (operational knowledge isn't derivable from code and otherwise leaks into ever-growing CLAUDE.md files) and `GLOSSARY.md`. The schema doc is named **AGENTS.md, not CLAUDE.md** — the one layer the skill insists is cross-tool should not carry a tool-specific filename; init creates a `CLAUDE.md` symlink (or `@`-import stub) so Claude Code still auto-loads it when working in the wiki tree, the exact [interop pattern](https://claudelog.com/faqs/claude-md-agents-md-symlink/) already cited in section 2. Two exclusions, stated as rules in the schema doc: **no reference/ category** ("do not store what an agent can regenerate from code in under a minute" — generalizing [C4's code-level guidance](https://c4model.com/diagrams/code) and [Diátaxis on auto-generated reference](https://diataxis.fr/reference/); the Aider repo-map lesson: [recompute, don't curate](https://aider.chat/docs/repomap.html)), and **no session/task state** (activeContext/progress/TODOs go to native agent memory or trackers; every memory bank that mixed them saw those files rot first — [Cline](https://docs.cline.bot/best-practices/memory-bank), [Beads](https://github.com/steveyegge/beads)). No tutorials/ — the onboarding guide is a derived connector artifact. `log.md` is adopted from the gist (the reference repo lacks it; it gives future sessions recency awareness for free). Curation pressure: a **soft page budget (~30–50)** reported by `check`, adjudicating DeepWiki's hard 30-cap against the reference repo's organic 39 — warn, don't block.

**Frontmatter schema (durable fields only):**

```yaml
title: Price sync pipeline
summary: One line, shown verbatim in the generated index and llms.txt
category: features          # one of the taxonomy dirs
kind: explanation           # explanation | how-to | reference-table | decision
audience: [dev]             # or [dev, ops] etc. — configurable taxonomy at init
read_when: "touching price agreements, UoM pricing, or the price reconcile timer"
covers:
  - path: packages/orchestrator/src/activities/upsertPrices.ts
    sha: 3f2a91c…           # git blob SHA, written by `wiki stamp`, verified by `wiki check`
generated_at_commit: d0225e0
last_refreshed: 2026-06-09
related: [concepts/uom-handling, flows/price-orchestrator]
```

Deliberate changes vs the reference repo: **`status:` and `last_checked:` are removed from frontmatter — and from the tracked tree entirely.** Status is always *computed* by the checker, which takes under a second from covers SHAs (the reference repo's 142-line checker proves it); there is no durable information in cached check results worth committing, so any `.llm-wiki/state.json` cache is gitignored. Committing volatile check-state would merely relocate the dirty-working-tree and merge-conflict disease from frontmatter into a single JSON file every branch touches. The committed, reader-visible freshness signal is a different artifact with different timing: connectors render "verified against `<short-sha>` on `<date>`" per page from `generated_at_commit`/`last_refreshed`, written at *refresh* time, not at check time. `read_when` is added per the Devin-trigger / Cursor-description pattern — it makes pages mechanically translatable into Cursor `.mdc` rules, Kiro fileMatch steering, and Copilot `applyTo` instruction files via connectors. `decisions/` pages add MADR-lite fields ([status, date, superseded-by](https://adr.github.io/madr/)) and are immutable-with-supersession while every other page is living — the dual mutability model is explicit, and the freshness check's answer to the [documented #1 ADR failure mode](https://www.javacodegeeks.com/2026/05/the-reason-most-architecture-decision-records-get-written-and-never-read-is-architectural-not-cultural.html) (stale ADRs "actively mislead") is: covered files of an accepted decision changed → prompt a superseding draft. Pages without mechanical anchors take optional `ttl_days` + reviewer byline (the [Google g3doc freshness-date practice](https://abseil.io/resources/swe-book/html/ch10.html)). Empty `covers` ⇒ reported `unmanaged` — keep the honest third state. Unknown frontmatter keys MUST be ignored by all tooling (extensibility contract).

### 5b. Onboarding / init flow

One command (`/llm-wiki:init`), two phases with a human checkpoint between them — the deepwiki-open plan-then-generate shape plus the approval gate every good system has ([Kiro Generate Steering Docs](https://kiro.dev/docs/steering/), Devin suggest-then-approve, Claude `/init`). Never silently write a wall of pages.

1. **Detect** (Boost pattern, [auto-detect before asking](https://laravel.com/docs/12.x/boost)): languages, package manager, monorepo layout, existing docs/, CLAUDE.md/AGENTS.md/copilot-instructions.md, existing ADRs, test/generated/vendored dirs (seed exclude globs), CI presence, git hooks manager.
2. **Ask ≤5 questions** with strong defaults (BMAD pattern; provide `--yes` non-interactive flags): wiki location/name; scope include/exclude globs (the key decision — including by-policy exclusions like UI-heavy code); audience taxonomy (default single `[dev]`); enable post-commit hook? (default yes, non-blocking — hooks aren't cloned with repos, so the blast radius is the initializing user only); seeding depth (manifest-only vs draft top-N pages now).
3. **Map**: fan out subagents per detected subsystem to build a feature-surface inventory (the reference repo's completeness-audit Phase 1 is effectively this flow already) — structure-aware walking of the import/dependency graph, **not** embedding retrieval (the CodeWiki-beats-RAG finding).
4. **Propose**: a page manifest (category/slug/one-line purpose/planned-vs-draft-now) shown for approval — the [.devin/wiki.json](https://docs.devin.ai/work-with-devin/deepwiki) shape, shipped as the default rather than an escape hatch.
5. **Generate**: vendor the scaffold (taxonomy dirs, templates, schema AGENTS.md from template with repo-specific slots + CLAUDE.md symlink, `wiki.config.yml`, the check scripts, REFRESH-PROMPT, hook); draft the approved pages with citations; run `wiki stamp` to write covers SHAs mechanically (the helper the reference repo lacks); run `wiki check` to green; regenerate `index.md`; write `.llm-wiki/manifest.json` (tool version, schema version, generated-file list + hashes).
6. **Wire entry points**: patch a ≤10-line pointer block into CLAUDE.md, AGENTS.md, and — when a Copilot setup is detected — `.github/copilot-instructions.md` ("orientation layer at `<path>`, start at index.md, code is source of truth, update pages when behaviour changes, run `wiki check`"); print next steps. Never inline wiki content into the root files ([hot/cold split](https://arxiv.org/abs/2602.20478)).

### 5c. Maintenance loop

**Architecture: three deterministic layers, then the LLM.** This is the load-bearing design decision, motivated by the implementation-drift evidence above: with a 7–42pp detection drop when only code changes, LLM judgment cannot be the trigger.

1. **Anchor check** (`wiki check`): re-hash every `covers` entry via `git hash-object`; classify fresh / stale / unmanaged / malformed. Zero-cost, offline, language-agnostic. Blob SHAs win the anchor trade-off: line ranges rot ([CodeTour "tour decay"](https://github.com/microsoft/codetour/issues/141)), symbol anchors need per-language tooling and miss body changes, embeddings are nondeterministic and patent-adjacent ([SAP US10977031B2](https://patents.google.com/patent/US10977031B2/en)) — and `git diff <old-sha> <new-sha>` reconstructs exactly what changed since verification. Add git-rename auto-resolution (`git log --follow`) as a Swimm-style silent auto-fix tier.
2. **Deterministic lints**: dangling-reference check — cited paths and backticked symbols must exist ([>25% of top-1000 repos carry at least one outdated code reference](https://arxiv.org/pdf/2307.04291); the cheapest, most embarrassing drift class); internal-link/orphan/index-sync checks (regenerate index.md and diff — the [terraform-docs pattern](https://terraform-docs.io/how-to/pre-commit-hooks/)); flow-validator plugins (5e); audience lint ([dev,X] page missing its `## For X` section — the enforcement gap the reference repo never closed); page-size lint (<500 lines, single-reviewer-sized). Mature link checkers exist ([lychee](https://lychee.cli.rs/), markdown-link-check, remark-validate-links), but they are either frontmatter-unaware or drag in npm/Rust toolchains the vendored layer forbids — the stdlib-only constraint justifies a ~50-line internal-links-only lint, with lychee documented as the escape hatch for full external-link checking.
3. **Coverage** (`wiki coverage`): scope globs minus all covers paths, grouped by dir, page-worthy clusters flagged; `--since <ref>` commit-time nudge; report a coverage % — frontmatter-declared, never embedding-inferred (auditable, and clear of the SAP patent's embedding-mapping claims). Plus an "uncovered hot files" view (churned recently, never covered) so missed nudges resurface — fixing the reference repo's miss-the-one-nudge gap.
4. **LLM refresh** (`wiki refresh`, flag-and-queue + batched): per stale page, feed the *precise diff* between recorded and current blob SHAs; triage no-op (re-stamp — the cheap path for cosmetic churn) / targeted edit / rewrite; re-verify every citation, demote unconfirmable claims to `TODO-VERIFY`; re-stamp covers; produce a **reviewable commit**, never silent mutation ("treat like code changes — require reviews", [Kiro](https://kiro.dev/docs/steering/)). This is RepoDoc-style minimal-scope regeneration with the covers list as a human-auditable degenerate impact map — decentralized in frontmatter, not a central mapping table (both [Dosu](https://dosu.dev/blog/how-to-catch-documentation-drift-claude-code-github-actions) and the [understandingdata recipe](https://understandingdata.com/posts/doc-drift-detection-ci/) flag the central table as a maintenance burden).

**Hooks, no CI assumption.** The check script is the source of truth — hooks aren't cloned with repos and CI can't be assumed. Ship: a **default-enabled (confirmed at init), non-blocking post-commit hook** (freshness + `--since` coverage nudge + lints, <1s, exit 0 always — blocking gates get uninstalled); a `wiki:install-hook` command (`core.hooksPath`); and an optional GitHub Action recipe as a *connector* (non-blocking stale-report job — the reference repo's admitted weakest link is local-only checking). Periodic complement: `wiki audit` — an on-demand LLM pass for what hashes can't catch (wrongness, duplication, contradictions, semantic drift; Karpathy's lint + [Malloy's verify-the-tree ritual](https://docs.malloydata.dev/blog/2026-01-13-context-md-convention/)), honestly documented as a separate drift class rather than pretending the per-commit loop catches it. Surface freshness to readers: connectors render "verified against `<short-sha>` on `<date>`" per page — visibly stale metadata makes accurate docs distrusted ([Fern](https://buildwithfern.com/post/docs-linting-guide)).

### 5d. Packaging

**Decision: a Claude Code plugin whose init skill vendors the per-repo layer.** Not a standalone npx installer (the SuperClaude lesson — [issue #419](https://github.com/SuperClaude-Org/SuperClaude_Framework/issues/419) enumerates the toolchain/update pain, and the ecosystem direction is installer→plugin migration), not dual-channel (oh-my-claudecode's `--plugin-dir-mode` complexity), and not pure marketplace-only like [superpowers](https://github.com/obra/superpowers) — that works for repo-agnostic process skills, but llm-wiki has per-repo state, so it needs the vendoring step superpowers deliberately avoids.

- **The plugin** carries the skills (`init`, `check`, `refresh`, `stamp`, `audit`, `connect`, `update`) and master script copies under `${CLAUDE_PLUGIN_ROOT}`. Init/update get `disable-model-invocation: true`; "consult the wiki before working" and "update the page when behaviour changes" are model-invoked with concrete trigger descriptions. All skills [agentskills.io-spec-compliant](https://agentskills.io/specification) (name==dir, ≤1024-char descriptions, llm-wiki-specific fields under `metadata:`) — the spec is adopted by ~40 tools, and [Cursor reads `.claude/skills/` directly](https://cursor.com/help/customization/skills), so optionally vendoring a small maintenance skill into the target repo reaches Cursor/Codex users with zero llm-wiki installation. AGENTS.md and copilot-instructions.md pointer blocks cover everything else.
- **The vendored layer** (committed to the target repo): wiki content + schema doc + config + the check scripts + hook. Scripts stay **stdlib-only (node + git), zero npm install** — frameworks get ripped out over toolchain weight and context bloat ([HN framework-wars thread](https://news.ycombinator.com/item?id=45155302)); the reference repo proves stdlib-only checkers suffice. The stdlib-only pledge is scoped precisely: the **vendored checkers parse the corpus directly** (frontmatter, headings, and relative links are line-parseable — the reference repo already does the frontmatter half) and **never depend on `wiki-index.json`**; the `wiki index` hub of 5e is a *plugin/connector-side* tool that may carry npm dependencies because it runs from the plugin install, never from the target repo's toolchain. All paths/tunables come from `wiki.config.yml`, which becomes machine-authoritative (fixing the reference repo's decorative-config flaw and its hardcoded-path rename pain).
- **Updates**: `.llm-wiki/manifest.json` stamps tool version + generated-file hashes at vendor time (the [BMAD manifest pattern](https://docs.bmad-method.org/how-to/install-bmad/)); `/llm-wiki:update` regenerates only files whose hash matches what it originally wrote and surfaces user-modified files for review — [Boost's regenerate-with-override-layer](https://laravel.com/docs/12.x/boost), inverted for committed content: **pages are the product and always committed; tooling is regenerable**. Document the split in the vendored README.
- **Versioning**: omit plugin.json `version` while iterating (commit-SHA mode — the [documented set-and-forget foot-gun](https://code.claude.com/docs/en/plugins-reference)); switch to semver + CHANGELOG once the frontmatter schema stabilizes; MAJOR bump = schema change, and `update` runs schema migrations on vendored repos.
- **Launch checklist**: own-repo `marketplace.json` (works day one via `/plugin marketplace add`), `claude plugin validate` in CI, [claude-community](https://github.com/anthropics/claude-plugins-community) submission, awesome-claude-code PR. No network calls at init time (BMAD's rate-limit lesson). A thin `npx llm-wiki init` shim that delegates to the same vendoring logic is v0.2+ at most.

Distribute in the gist's spirit: the schema doc explicitly invites the agent to adapt taxonomy/categories to the repo during init — rigid generators are this category's failure mode, and tiny opinionated quotable defaults are its growth vector ([forrestchang's ~70-line CLAUDE.md → 220k combined stars](https://www.techtimes.com/articles/316798/20260518/karpathy-inspired-claudemd-passes-220000-combined-github-stars-four-rules-that-stop-ai-breaking.htm)).

### 5e. Connector architecture

**The contract is two-tier, and both tiers are versioned — connectors declare which tier and version they consume.**

**Tier A — the corpus contract** (`corpus_contract: v1` in the manifest), four guarantees: (1) layout — one wiki root, category subfolders, generated index.md; (2) links — plain relative `.md` links, no wikilinks in the canonical store (the one format GitHub, Obsidian, Quartz, Docusaurus, VitePress, Starlight all resolve; wikilink conversion is [mechanical both directions](https://github.com/zoni/obsidian-export)); (3) syntax — CommonMark+GFM, diagrams exclusively in fenced ```mermaid blocks ([GitHub renders them natively](https://github.blog/developer-skills/github/include-diagrams-markdown-files-mermaid/) — making GitHub's renderer connector #0, zero build); (4) frontmatter per the published schema, unknown keys ignored. Corpus-level connectors — the GitHub renderer, llms.txt, Quartz/Starlight sites — consume the markdown tree directly under these four guarantees and need nothing else. Pages carry frontmatter `title` *and* a matching body H1; SSG connectors strip the H1 — write this down, it's the most common silent multi-renderer breakage.

**Tier B — the index contract**, for staleness-aware connectors (MCP server, CI dashboards, rules emitters): `wiki index` parses the corpus once (remark/mdast — plugin-side, per 5d; the vendored checkers never depend on it) into a normalized **`wiki-index.json`** — pages, validated frontmatter, heading outlines, resolved link graph, Mermaid inventory, covers/staleness data. Because the index *is* the interface these connectors consume, its schema is itself the published, versioned artifact: a JSON Schema shipped with the plugin, `contractVersion` embedded in every emitted file, additive-only changes within a major version. Without this, "third parties add connectors without coordinating" would mean coupling to skill internals — the exact failure the contract exists to prevent. The reader→intermediate→writers shape is the convergent design of [Pandoc](https://pandoc.org/MANUAL.html), [unified](https://unifiedjs.com/learn/guide/introduction-to-unified/), [Quartz's transformer/filter/emitter pipeline](https://quartz.jzhao.xyz/advanced/making-plugins), and [Velite](https://github.com/zce/velite); it gives N+M instead of N×M economics. The `audience` field is a first-class filter at the pipeline's filter stage (generalizing [vitepress-plugin-llms's llm-only/llm-exclude gating](https://github.com/okineadev/vitepress-plugin-llms)), so per-audience artifacts derive from one corpus.

**Ship order:** **#0** GitHub renderer (free, by Tier A). **#1** llms.txt (Tier A) — emit the cross-ecosystem output triple byte-compatibly (llms.txt index + llms-full.txt concat + per-page .md, matching [vitepress-plugin-llms](https://github.com/okineadev/vitepress-plugin-llms)/[docusaurus-plugin-llms](https://github.com/rachfop/docusaurus-plugin-llms)); the generated index.md is already llms.txt-shaped, and the README states honestly that [no crawler consumes it](https://www.seroundtable.com/google-does-not-endorse-llms-txt-40789.html) — it's an agent entrypoint and portable wiki dump. **#2** Static site via **Quartz** (Tier A: arbitrary frontmatter tolerated, md links + Mermaid + backlinks + search built in, `-d` flag means content never moves); Starlight as documented alternative (needs `docsSchema({extend})` + [astro-mermaid](https://www.npmjs.com/package/astro-mermaid)); exclude [Material for MkDocs (maintenance mode since Nov 2025)](https://github.com/squidfunk/mkdocs-material/issues/8523) and mdBook (no frontmatter parsing). **#3** MCP (Tier A initially) — a config recipe pointing [docs-mcp-server](https://github.com/arabold/docs-mcp-server) or [mcp-server-markdown](https://github.com/ofershap/mcp-server-markdown) at the wiki root; a custom server with staleness/coverage/link-graph tools is the first true Tier B consumer, built on wiki-index.json only when justified. **#4+** (later, Tier B): onboarding-guide composer, Cursor-rules/Kiro-steering/Copilot-`applyTo` emitters from `read_when` + covers globs, RAG chunker (heading-bounded, ~512–1024 tokens, frontmatter as chunk metadata — [established best practice](https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/)), CI recipe.

**Rules for connectors:** each is a separate, independently versioned, replaceable module declaring which contract tier and version it consumes (connector targets *will* churn — Contentlayer died, MkDocs Material froze); every derived artifact must be regenerate-and-diff verifiable (the terraform-docs/[embedme --verify](https://github.com/zakhenry/embedme) pattern), which is also how generated index.md and llms.txt are kept honest.

**Flow-validator plugins** (the diagram differentiator): ship the reference repo's checker as a generic harness — page declares `flow-meta` (kind + anchors), config registers `validators: [{kind, script, contract: set-equality | anchor-existence}]`, extractors are dual CLI/`--json` modules loaded from user space. Ship two example extractors and document the honesty gradient and the enabling precondition (anchors must be mechanically extractable string literals/attributes in the target codebase). The same `--json` ground truth feeds generation prompts, validation, and human inspection — the extract-first / generate-with-ground-truth-injected / adversarially-verify / deterministic-gate recipe from the reference repo's workflows generalizes to any LLM-generates-machine-validates artifact.

## 6. Risks and open questions

- **Hallucination survives citations.** Auto Wiki and DeepWiki prove citations alone don't prevent fabrication. Mitigations: citation discipline + TODO-VERIFY demotion, the `wiki audit` adversarial pass, human review on refresh commits. A true claim-vs-cited-content verifier (no competitor has one) is an open v0.2+ research item.
- **SHA churn / refresh-by-rote.** Byte-coarse hashes flag cosmetic changes; the documented production failure is agents bumping SHAs without re-reading code, eroding citation trust. The no-op-vs-edit triage with the diff injected helps; symbol-level anchors (tree-sitter) would cut false positives but add per-language deps — deferred, explicitly.
- **Name collision.** "llm-wiki" defaults to Karpathy's *personal* KB pattern in the discourse; without the one-line repo-application positioning the README will confuse. Also consider whether to claim the name at all vs e.g. `repo-wiki`. **RESOLVED 2026-06-10: named `repolore`** after a dedicated naming-collision research pass — "repo" carries the derived-from-code signal, "lore" is the term AI engineers already use for tribal knowledge (namespace heating up, unowned: npm free in both spellings, no products, only dead 0–1★ repos). Killed alternatives: `agentwiki` (two live products + npm `agent-wiki` MCP + existing Claude Code skill), `cartographer` (586★ same-purpose Claude Code plugin), `engram`/`memex`/`atlas`/`primer`/`grimoire`/`fieldguide` (all owned by funded products or multi-k★ projects). The Karpathy hook stays in the tagline, not the name.
- **Coverage-ratchet patent adjacency.** [SAP US10977031B2](https://patents.google.com/patent/US10977031B2/en) covers embedding-based code↔doc mapping with commit blocking. Frontmatter-declared coverage + non-blocking reporting is both safer and more auditable; keep it that way.
- **Cross-tool reality.** Claude Code is the only first-class host today; Cursor reads vendored skills; Copilot teams get the `.github/copilot-instructions.md` pointer block, and path-scoped `*.instructions.md` `applyTo` globs map naturally from `read_when` + covers for a future emitter. What remains untested is depth, not reach: whether a Copilot-only team actually follows the index pointer into the wiki, with no skill machinery nudging them.
- **Monorepos.** "Closest AGENTS.md wins" suggests per-package index stubs; whether one wiki with scoped covers or nested wikis is right is unresolved — ship single-wiki + per-package index stubs as the default, revisit.
- **Scale.** Index navigation suffices to ~100 pages (gist); past that, recommend local search (BM25, e.g. qmd) rather than embedding infra. The generated-index design removes the single-writer bottleneck, but the page-budget warning needs field testing.
- **Deletion/archival.** No system surveyed has a story for removed features. Proposal to validate: feature page → `status: historical` + moved summary into log.md, never silent deletion.
- **Research-angle disagreements adjudicated above**, for the record: hard page cap (DeepWiki) → soft budget; howto/+glossary (doc-frameworks) → adopted over reference repo's six; Dosu numeric scoring → deferred behind the simpler three-state model; npx installer (BMAD precedent) → demoted to optional v0.2+ shim; Karpathy's ingest/query/lint verbs → kept as conceptual framing, mapped to concrete commands (init/refresh = ingest, page-filing = query's compounding half, check/audit = lint). **Adversarial-review adjudications** folded into this final version: committed check-state → gitignored/dropped (status is recomputable); stdlib-only pledge scoped to the vendored layer with the index hub explicitly plugin-side; the connector contract extended to version `wiki-index.json` itself; v0.1 cut from eight workstreams to the minimum thesis-proving loop; autodoc added as 2023 prior art; the TRACE drift statistic corrected to the paper's actual 7–42pp figure.
